# A/B промптів (Task E, bonus)

**Задача (на `app/`):** додати валідацію вхідних даних у
`app/src/money.ts :: applyDiscount`.

**Метод:** обидва промпти виконані **реальними агентами** (Claude Code, Opus 4.8)
у тому самому чистому дереві, по черзі, з відкатом між запусками. Метрики
(токени / tool-uses / час) — фактичні з телеметрії запуску; код — їхній реальний
diff. Тести зганялись `cd app && npm test`.

## Промпт A — базовий (слабкий)

```
зроби валідацію в applyDiscount
```

Жодного scope, AC, конвенцій, стоп-правила — агент сам вирішує «що» і «коли готово».

## Промпт B — структурований (`prompts/harden-input.md`)

```
Role: TS engineer in this repo (Node 22, vitest). Defensive, test-backed.
Goal: Validate inputs of applyDiscount and reject invalid values clearly.
Context: applyDiscount(cents, percent) does no range check; percent must be 0–100.
  parseAmount already throws on bad input — match that error style.
Constraints:
- Throw a descriptive Error on invalid input; do NOT change valid-path results.
- Add tests for each new guard (out-of-range, NaN, non-finite).
- Touch only the target fn + its test. No new deps. No secrets/PII.
Acceptance criteria:
- Out-of-range / NaN percent throws; valid cases unchanged.
- `cd app && npm test` green.
Output: Changed source + tests + a one-line note of the guards added.
Stop rules: If a guard would change an existing passing test's value, STOP and ask.
```

## Порівняння (реальні дані з запусків)

| Критерій | Промпт A (слабкий) | Промпт B (структурований) |
|---|---|---|
| Ітерацій до прийняття | 1 (прийнятно з першого разу) | 1 (прийнятно з першого разу) |
| Output токени (факт, subagent total) | **30 424** | **29 576** |
| Tool-uses / час | 8 / 87.7 s | 7 / 88.0 s |
| Рядків змінено в `money.ts` | **+12** (4 guard-блоки) | **+3** (1 guard) |
| Нових тест-кейсів | 4 | **5** (по одному на поведінку) |
| `npm test` | pass — 8 passed | pass — 9 passed |
| Що валідував | `percent` (0–100, finite) **+ `cents`** (finite, integer) | **тільки `percent`** (0–100, finite) — точно за scope |
| Стиль помилки | власний (не як у репо) | **узгоджений з `parseAmount`** (за Context) |
| Правки безпеки/валідації | додав сам (не просили окремо) | **гарантовано** як Acceptance criteria |
| Blast radius / scope | ширший: змінив контракт і для `cents` (не просили) | мінімальний, рівно ціль |

## Спостереження

1. **Обидва спрацювали** — і це головний нюанс. Сильна модель + хороший контекст
   репо (`AGENTS.md`/`CLAUDE.md` із Task D) «витягнули» навіть слабкий промпт:
   робочий код, валідація, тести, без читання `.env`. Тобто на сильній моделі
   різниця — **не «зламано vs працює»**.
2. **Де структура реально виграла:**
   - **Scope-контроль:** B змінив рівно ціль (`+3` рядки, лише `percent`); A «з
     доброти» додав ще валідацію `cents` (finite+integer) — **незапитану зміну
     контракту**, що може зламати викликачів із дробовими cents. `+12` vs `+3`.
   - **Узгодженість:** B зматчив стиль помилки `parseAmount` (бо Context сказав);
     A вигадав свій формат — дрейф конвенцій у кодбазі.
   - **Гарантія, а не везіння:** B мав валідацію як **AC** → відтворювано на
     будь-якій моделі/запуску; A отримав її завдяки дефолтам моделі → **не
     гарантовано** на слабшій моделі чи в іншому інструменті.
   - **Стоп-правило:** B мав явний guard «не міняй існуючі passing-тести».
3. **Вартість майже однакова** (30.4k vs 29.6k токенів) — структура **не дорожча**
   за слабкий промпт на цій задачі; «інвестиція» в текст промпту окупається без
   токенового штрафу.

## Висновок

На сильній моделі з добрим контекстом слабкий промпт не «провалився» — але дав
**ширший, менш узгоджений і непередбачуваний** результат (незапитана зміна
контракту `cents`, власний стиль помилок). Структурований за ту саму ціну дав
**контрольований scope, узгодженість із кодбазою і гарантовану валідацію як
критерій приймання**. Тобто цінність структури — не в «чи запрацює», а в
**передбачуваності, безпеці та повторюваності**; вона зростає тим більше, чим
слабша модель, більша задача й важливіша командна повторюваність.
