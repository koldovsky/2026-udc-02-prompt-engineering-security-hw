# A/B промптів (Task E, bonus)

Задача (на `app/`): додати функцію `applyTax(cents, percent)` у
`app/src/money.ts` — податок за аналогією з наявною `applyDiscount`, плюс
тести.

## Промпт A — базовий

> додай функцію applyTax в money.ts

## Промпт B — структурований

> **Role:** Ти — контрибʼютор до `app/src/money.ts` (money utilities module),
> що дотримується конвенцій `app/AGENTS.md`.
>
> **Context:** Файл оперує сумами у **integer cents**. Уже є `applyDiscount`
> — знижка з валідацією `percent ∈ [0, 100]` через `assertPercentInRange` і
> округленням `Math.round`. Потрібна симетрична функція для податку.
>
> **Constraints:**
> - Не змінюй існуючі експортовані функції та їх сигнатури.
> - Використовуй ту саму валідацію (`assertPercentInRange`), а не нову.
> - Округлення — до найближчого цента (`Math.round`), як у `applyDiscount`.
> - Без нових залежностей, без float-обчислень поза `Math`.
>
> **Acceptance criteria:**
> - `applyTax(cents, percent)` повертає `cents`, збільшені на `percent`%.
> - Кидає `RangeError`, якщо `percent` поза `[0, 100]`.
> - JSDoc у тому ж стилі, що й `applyDiscount`.
> - Тести в `money.test.ts`: звичайний випадок, округлення, `0%` (no-op),
>   `percent` поза межами.
> - `cd app && npm test` — усі тести зелені.
>
> **Output:** тільки diff у `app/src/money.ts` і `app/src/money.test.ts`,
> без пояснювального тексту поза кодом.

## Порівняння

| Критерій | Промпт A | Промпт B |
|---|---|---|
| Ітерацій до прийняття | 2 (перша спроба без валідації → окрема правка-фікс) | 1 |
| Output токени (≈) | ~40 (5 рядків коду, без JSDoc, без тестів) на ітерацію 1; +~60 на ітерацію 2 (виправлення) → ~100 сумарно | ~180 (функція + JSDoc + 4 тест-кейси) за один прохід |
| Якість результату | Мінімальна: працює для «нормального» вводу, але без документації й без тестів | Повна: JSDoc, узгоджено з конвенціями модуля, вкрито тестами |
| Правки безпеки/валідації | **Не враховано одразу** — перша спроба (`Math.round(cents * (1 + percent / 100))` без виклику `assertPercentInRange`) мовчки приймала від'ємний або >100% `percent`, що дає некоректний або "негативний податок" результат без помилки; довелось окремо просити додати перевірку | **Враховано одразу** — `assertPercentInRange` викликано в першій же версії, бо це було явним constraint |

## Деталі experiment A (ітерація 1 → 2)

Ітерація 1 (буквально за промптом «додай функцію applyTax в money.ts», без
додаткового контексту) дала:

```ts
export function applyTax(cents: number, percent: number): number {
  return Math.round(cents * (1 + percent / 100));
}
```

Проблеми: немає валідації `percent` (симетрія з `applyDiscount` порушена —
там валідація є), немає JSDoc, немає тестів. `applyTax(10000, -50)` мовчки
поверне `5000` замість кидання помилки — неконсистентно з рештою модуля.

Ітерація 2 (окремий follow-up: «додай валідацію як у applyDiscount і тести»)
довела реалізацію до того ж вигляду, що промпт B дав одразу — тобто інвестиція
в структурований промпт по суті замінила один явний раунд правок.

Фінальна версія в кодовій базі (`app/src/money.ts`, `app/src/money.test.ts`)
відповідає результату промпту B: `applyTax` з `assertPercentInRange`, JSDoc і
4 тест-кейсами; `cd app && npm test` — 18/18 зелені.

## Висновок

Структурований промпт (B) окупився саме на **правках безпеки/валідації**:
базовий промпт (A) з першої спроби видав функцію, що мовчки приймає
некоректний вхід (від'ємний/надлишковий `percent`) — тиху розбіжність з
контрактом сусідньої `applyDiscount`, яку легко не помітити без окремого
рев'ю. Структурований промпт заклав ту саму вимогу як явний constraint і AC,
тому дав коректний, задокументований і покритий тестами результат за один
прохід замість двох. Різниця найпомітніша не в обсязі коду, а в **кількості
ітерацій до "прийнятного" результату**: 1 проти 2, де другий раунд промпту A
— це, по суті, компенсація відсутньої валідації, яку структурований промпт
попереджає заздалегідь.
