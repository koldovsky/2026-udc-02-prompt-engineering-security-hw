# A/B-експеримент: генерація функції нарахування податку

**Завдання:** додати до `app/src/money.ts` функцію (або функції) для обчислення суми податку та загальної суми з ПДВ.

---

## Промпт A — базовий

> Створи функцію для нарахування відсотка податку

**Що отримали за один запит:**

- `taxAmount(cents, percent)` — повертає суму податку в центах (округлення)
- `applyTax(cents, percent)` — повертає суму разом із податком
- JSDoc з прикладами для обох функцій
- Валідація `cents ≥ 0` та `0 ≤ percent ≤ 100` з людиночитаними повідомленнями
- 10 нових тестів (29 усього — всі пройшли)

---

## Промпт B — структурований

```
Role: Ти TypeScript-розробник у фінтех-продукті.

Context: У модулі money.ts вже є тип Cents (ціле число, копійки). Потрібна
функція для розрахунку суми ПДВ від ціни товару.

Constraints:
- Вхідні значення — тільки Cents (невід'ємне ціле)
- Ставка податку — number від 0 до 1 (наприклад, 0.2 для 20%)
- Округлення — Math.round, не Math.floor
- Не використовуй float для проміжних грошових розрахунків

Acceptance Criteria:
- calculateTax(1000, 0.2) → 200
- calculateTax(999, 0.2) → 200 (округлення вгору)
- Кидає помилку для від'ємного Cents або rate поза [0, 1]

Output: TypeScript-функція з JSDoc і unit-тестом на Jest.
```

**Що отримали за один запит:**

- `calculateTax(cents, rate)` — одна функція, rate у діапазоні 0–1 (як і задано)
- JSDoc з `@throws`, `@example` для обох AC-кейсів
- `RangeError` (семантично точніше, ніж `Error`) без нагадування
- Арифметика лишилась у цілих центах: `Math.round(cents * rate)` без float-конверсії
- 8 нових тестів (37 усього — всі пройшли), усі три guard-кейси покриті

## Порівняння

| Критерій | Промпт A | Промпт B |
|---|---|---|
| Ітерацій до прийняття | **1** | **1** |
| Output-токени (≈) | **~700** | **~600** |
| Якість результату | Висока: 2 функції, JSDoc, тести, але API визначено довільно (percent 0–100) | Дуже висока: точно 1 функція, API строго за специфікацією (rate 0–1), `RangeError` |
| Правки безпеки / валідації | Додано без нагадування, але тип помилки — `Error` | Усі обмеження закладено в промпт; модель обрала `RangeError` самостійно |

> **Примітки до Промпту A:**
> Модель вивела дві функції замість однієї (`taxAmount` + `applyTax`) — розпізнала паттерн `applyDiscount` із контексту файлу і відтворила той самий стиль. Валідацію та тести додала без нагадування.

> **Примітки до Промпту B:**
> Завдяки явним Constraints і Acceptance Criteria модель не «вигадувала» API: одна функція, rate 0–1, тести прямо по AC-кейсах. `RangeError` замість `Error` — приклад того, як точний контекст (фінтех, Cents-брендинг) підштовхує до кращих рішень навіть без прямої вказівки.

---

## Висновок

Обидва промпти дали робочий результат з першої ітерації — але **якість API різниться суттєво**.

Промпт A покладається на здогадки моделі: вона правильно відтворила стиль модуля, але обрала `percent`-API (0–100) замість `rate`-API (0–1) та повернула дві функції. У реальному проєкті це потребувало б уточнення або рефакторингу.

Промпт B усував неоднозначність на вході: Role → Context → Constraints → AC → Output. Модель не мала простору для «творчої інтерпретації» і витратила менше токенів (менше пояснень-«здогадок»). Додаткова вигода — явні AC стали готовими назвами тестів, що скоротило обсяг тест-коду.

**Практичний висновок:** для продуктового фінтех-коду структурований промпт із Constraints і Acceptance Criteria дає вищу передбачуваність і менше правок post-review, навіть якщо сам промпт довший. Базовий промпт виправданий лише для розвідувальних запитів («що взагалі можна зробити?»), а не для чіткого завдання з вимогами до безпеки.
