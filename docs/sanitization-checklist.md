# Чек-ліст санітизації даних для AI (команда: Payments)

> Багаторазовий документ. Перед тим як дати будь-який внутрішній текст
> (тікет, лог, код, скріншот) в AI-інструмент — пройди цей чек-ліст зверху вниз.
> Правило №0: **сумнів → стався як до 🔴.**

## 1. Класифікуй (світлофор)

- [ ] **🔴 Ніколи публічним:** секрети (ключі, токени, паролі, connection strings),
      PII (ім'я, email, телефон, ДН, паспорт, ІПН), банківська таємниця
      (картка, CVV, IBAN, рахунок, баланс), production-дані/дампи,
      медичні/держ./регульовані дані.
- [ ] **🟡 Лише enterprise/no-train:** внутрішній код під NDA, бізнес-логіка,
      схеми БД, архітектура, тікети з контекстом, анонімізовані логи.
- [ ] **🟢 Можна публічним:** публічний/OSS-код, синтетика, загальні питання,
      документація без даних, стек-трейс без значень.
- [ ] Сумнів → вважати 🔴.

### Швидкий пошук 🔴 (grep-патерни перед відправкою)

- [ ] `KEY|TOKEN|SECRET|PASSWORD|Bearer|sk-` — ключі/токени
- [ ] `postgres://|mysql://|mongodb://|amqp://` — connection strings
- [ ] `\b\d{4}[ -]?\d{4}[ -]?\d{4}[ -]?\d{4}\b` — номери карток
- [ ] `[A-Za-z0-9._%+-]+@` — email
- [ ] `\+?\d[\d ()-]{8,}` — телефони / IBAN / рахунки

## 2. Очисти (техніка відповідно до категорії)

- [ ] **Redaction** — прибрати повністю (`[REDACTED]`): те, що не потрібне задачі
      (CVV, паспорт, ДН).
- [ ] **Masking** — зберегти формат, прибрати значення (`****-1234`, `<IBAN>`):
      коли моделі потрібна структура.
- [ ] **Synthetic** — підмінити реалістичним вигаданим (`[CUSTOMER_1]`,
      `customer-1@example.test`): коли потрібні «справжні на вигляд» дані.
- [ ] **Секрети — out-of-band:** не маскувати, а **не давати взагалі**
      (env / secret store); якщо «світилися» — **ротувати негайно**.

## 3. Перевір перед відправкою

- [ ] Чи можна реідентифікувати людину з решти полів? (ім'я+ДН+місто+посада)
- [ ] Чи не несе чутливе вставлений URL / скріншот / лог?
- [ ] Чи збережена **задача** після санітизації? (модель ще розуміє баг)
- [ ] Чи відповідає інструмент/tier категорії даних? (no-train для 🟡)
- [ ] Чи робив я санітизацію **локально**, а не вставляючи оригінал у публічну модель?

## 4. Інструмент за категорією

| Категорія | Дозволений інструмент / tier | Нотатки |
|---|---|---|
| 🟢 | Будь-який (ChatGPT, Claude, Copilot — free/pro) | Дані не чутливі. |
| 🟡 | Copilot Business / Claude for Work / ChatGPT Enterprise — **no-train + data residency** | Лише після санітизації PII. |
| 🔴 | **Не давати моделям.** Лише локально / маскувати до 🟡/🟢, секрети — ротувати | Out-of-band обов'язково. |

### Чому саме цей tier для 🟡 (обґрунтування)

Для 🟡-даних (внутрішня логіка, тікети з контекстом, анонімізовані логи) ми
обираємо **enterprise-tier із гарантією no-train** (напр. Claude for Work /
Copilot Business / ChatGPT Enterprise), бо:

- **No-train** — провайдер не використовує наші промпти для тренування моделей,
  тож внутрішня логіка не «протече» в чужі відповіді.
- **Data residency / DPA** — є договір на обробку даних і контроль регіону
  зберігання, що важливо для фінансового домену (банківська таємниця поруч).
- **Аудит і ретеншн** — логи доступу й короткий строк зберігання промптів.

Безкоштовні/споживчі tiers для 🟡 **не використовуємо**, бо за замовчуванням
можуть тренуватись на введених даних і не дають договірних гарантій.

## 5. Якщо стався витік

- [ ] Ротувати скомпрометовані секрети негайно.
- [ ] Нотифікувати відповідального (security/lead).
- [ ] Зафіксувати інцидент і оновити цей чек-ліст.
