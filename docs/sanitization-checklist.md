# Чек-ліст санітизації даних для AI (команда: payments-core)

> Багаторазовий чек-ліст перед вставкою тікетів, логів або CRM-даних у промпт,
> PR-опис або публічну AI-модель. Приклад застосування: `docs/sanitized-ticket.md`
> (оригінал — `materials/sensitive-ticket.md`).

## 0. Що шукати в документі

Пройдіться по тексту й позначте збіги. Сумнів → вважати 🔴.

| Патерн / тип | Приклади (не вставляти як є) | Категорія |
|---|---|---|
| API-ключі, токени | `X-API-Key:`, `sk-live-…`, `Bearer …`, `ghp_…` | 🔴 |
| Connection strings | `postgres://user:pass@host:5432/db`, `mongodb+srv://…` | 🔴 |
| ПІБ, email, телефон | `Іваненко`, `@gmail.`, `+380 …` | 🔴 |
| ДН, паспорт, ІПН | `ДН:`, `РНОКПП`, `ІПН:`, серія/номер паспорта | 🔴 |
| Платіжні дані | PAN картки, `CVV`, `exp MM/YY`, `IBAN`, баланс рахунку | 🔴 |
| Production-контекст | `production-лог`, `*_prod`, внутрішні IP (`10.x.x.x`) | 🔴 |
| Внутрішні сервіси / код | `FeeCalculator`, `payments-core`, назви гілок | 🟡 |
| Суть задачі без даних | опис бага, acceptance criteria, очікувана поведінка | 🟢 |

## 1. Класифікуй (світлофор)

- [ ] **🔴 Ніколи публічним:** секрети (ключі, токени, паролі, connection strings),
      PII (ім'я, email, телефон, ДН, паспорт, ІПН), банківська таємниця
      (картка, CVV, IBAN, рахунок, баланс), production-дані/дампи,
      медичні/держ./регульовані дані.
- [ ] **🟡 Лише enterprise/no-train:** внутрішній код під NDA, бізнес-логіка,
      схеми БД, архітектура, тікети з контекстом, анонімізовані логи.
- [ ] **🟢 Можна публічним:** публічний/OSS-код, синтетика, загальні питання,
      документація без даних, стек-трейс без значень.
- [ ] Сумнів → вважати 🔴.

## 2. Очисти (техніка під категорію)

| Категорія | Техніка | Плейсхолдер / приклад |
|---|---|---|
| 🔴 PII (ім'я) | Masking | `[CUSTOMER_1]`, `[CUSTOMER_2]` |
| 🔴 Email / телефон | Synthetic | `customer_1@example.test`, `+380 00 000 00 00` |
| 🔴 Картка | Masking | `****-1234`; CVV → `[REDACTED]`; exp → `[REDACTED]` |
| 🔴 IBAN / рахунок | Masking | `<IBAN>`; у логах `account=<IBAN>` |
| 🔴 Баланс | Masking / redaction | `<BALANCE>` або `[REDACTED]` |
| 🔴 ДН, паспорт, ІПН | Synthetic або redaction | `[DOB]` / `01.01.1980`, `ХХ 111111`, `[REDACTED]` |
| 🔴 Суми в логах (якщо не потрібні) | Masking | `amount=хххх.00` — залишити лише поля, важливі для бага |
| 🔴 Секрети | **Out-of-band** | `<SECRET_OUT_OF_BAND>` у тексті; значення — лише в vault / `.env` (не в промпт) |
| 🔴 Production dump | Redaction | прибрати рядки з credentials; залишити структуру події |
| 🟡 Внутрішня логіка | Залишити або узагальнити | назви класів OK у enterprise-tier; у публічному — «fee service» без гілки |

Правила:

- [ ] **Redaction** — прибрати повністю (`[REDACTED]`): те, що не потрібне задачі.
- [ ] **Masking** — зберегти формат, прибрати значення (`****-1234`, `<IBAN>`):
      коли моделі потрібна структура.
- [ ] **Synthetic** — підмінити реалістичним вигаданим: коли потрібні «справжні
      на вигляд» дані для відтворення.
- [ ] **Секрети — out-of-band:** не маскувати частково (`sk-live-****`), а **не давати
      значення взагалі** (env / secret store / 1Password); у документі — лише
      `<SECRET_OUT_OF_BAND>`. Якщо секрет уже потрапив у чат — **ротувати**.
- [ ] Після санітизації **задача збережена**: баг, кроки відтворення (без PII),
      acceptance criteria залишаються зрозумілими.

## 3. Перевір перед відправкою

- [ ] Чи можна реідентифікувати людину з решти полів? (ім'я + ДН + місто + посада)
- [ ] Чи не несе чутливе вставлений URL / скріншот / лог / вкладення?
- [ ] Чи немає «часткових» витоків (`UA90…789`, `sk-live-9f3a…`, `S3cr3t-P@ss`)?
- [ ] Чи збережена **задача** після санітизації? (модель розуміє баг без оригіналу)
- [ ] Чи відповідає інструмент/tier категорії даних? (no-train для 🟡)
- [ ] Оригінал з 🔴-даними **не** вставляти в публічну модель — санітизувати
      локально (вручну або скриптом) і в промпт лише `docs/sanitized-ticket.md`.

## 4. Інструмент під категорію

| Категорія | Дозволений інструмент / tier | Нотатки |
|---|---|---|
| 🟢 | Публічний ChatGPT / Claude / Copilot Free; Cursor без контексту з секретами | Загальні питання, OSS-код, AC без даних |
| 🟡 | Cursor (Privacy Mode) / Copilot Business / Claude for Work — **no-train**; enterprise з data residency | Внутрішні тікети, назви сервісів (`payments-core`), гілки, фрагменти бізнес-логіки |
| 🔴 | **Не давати моделям.** Локальна санітизація → потім лише 🟢/🟡 шар у промпт | Секрети — out-of-band; PII/картки/IBAN — masking/redaction/synthetic |

### Рішення для 🟡-даних (Task B, п.4)

**Обраний інструмент:** **Cursor Teams або Enterprise** (не «Cursor (Business)») з **team-wide Privacy Mode** для всіх 🟡-даних; якщо потрібна **data residency** — лише **Cursor Enterprise**. Перед використанням має бути підписаний **DPA**. Альтернатива: GitHub Copilot Business або Claude for Work з контрактом enterprise.

**Чому саме цей tier:**

| Критерій | Як закриваємо |
|---|---|
| **No-train** | Team-wide Privacy Mode / enterprise-угода: промпти з 🟡-контекстом не використовуються для тренування моделей постачальника. |
| **Enterprise** | Доступ лише для аутентифікованих учасників команди; аудит і політики від security, не consumer-акаунт. |
| **Data residency** | Якщо residency обов'язкова — лише **Cursor Enterprise** (Teams її не гарантує). Перед передачею 🟡-даних: DPA + підтвердити з постачальником регіон, які етапи обробки він покриває (inference / зберігання / логи), які моделі й функції доступні в цьому режимі. Регіональне покриття може бути частковим (напр. лише inference і за запитом) — фіксуємо обмеження письмово. |

**Приклад з нашого тікета:** після санітизації в промпт можна давати блок «Внутрішня логіка»
(`FeeCalculator.applyTransferFee()`, `preAuthorize()` / `settle()`, гілка `feat/PSD2-fee-refactor`,
компонент `payments-core`) — це 🟡, не 🔴. Такий текст **не** вставляємо в публічний ChatGPT
або Copilot Free: там немає гарантій no-train і NDA-контуру.

**Правило:** спочатку прибрати весь 🔴 (`docs/sanitized-ticket.md`), потім 🟡-шар — лише в
enterprise/no-train інструменті. Якщо enterprise недоступний — узагальнити 🟡 до 🟢
(«fee додається двічі в pre-auth і settle» без назв класів і гілок).
