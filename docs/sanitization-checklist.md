# Чек-ліст санітизації даних для AI (команда: payments-core)

> Скопійовано з `docs/templates/sanitization-checklist.md` і доповнено на
> прикладі `materials/sensitive-ticket.md` → `docs/sanitized-ticket.md`.
> Мета — багаторазовий документ, який можна принести колегам.

## 1. Класифікуй (світлофор)

- [x] **🔴 Ніколи публічним:** секрети (ключі, токени, паролі, connection strings),
      PII (ім'я, email, телефон, ДН, паспорт, ІПН), банківська таємниця
      (картка, CVV, IBAN, рахунок, баланс), production-дані/дампи,
      медичні/держ./регульовані дані.
      Приклад: `X-API-Key: sk-live-...`, `postgres://payments:S3cr3t-P@ss@...`,
      ПІБ клієнта, картка/IBAN/баланс, паспорт/ІПН.
- [x] **🟡 Лише enterprise/no-train:** внутрішній код під NDA, бізнес-логіка,
      схеми БД, архітектура, тікети з контекстом, анонімізовані логи.
      Приклад: назва компонента `FeeCalculator.applyTransferFee()`, гілка
      `feat/PSD2-fee-refactor`, опис бага в `preAuthorize()`/`settle()`.
- [x] **🟢 Можна публічним:** публічний/OSS-код, синтетика, загальні питання,
      документація без даних, стек-трейс без значень.
      Приклад: "комісія нараховується двічі за переказ", acceptance criteria
      без конкретних сум/ID.
- [x] Сумнів → вважати 🔴.

## 2. Очисти (техніка під категорію)

- [x] **Redaction** — прибрати повністю (`[REDACTED]`): те, що не потрібне задачі
      (email репортера, паспорт, ІПН, дата народження, CVV, host у логах).
- [x] **Masking** — зберегти формат, прибрати значення (`****-1234`, `<IBAN>`):
      коли моделі потрібна структура (номер картки, IBAN, сума в логах,
      формат телефону).
- [x] **Synthetic** — підмінити реалістичним вигаданим: коли потрібні «справжні
      на вигляд» дані для відтворення (ім'я → `[CUSTOMER_1]`, ID тікета/txn
      можна лишити, бо це не PII).
- [x] **Секрети — out-of-band:** не маскувати, а **не давати взагалі**
      (env / secret store) — замінюємо на `<SECRET_OUT_OF_BAND>`; якщо
      «світилися» в логах — ротувати негайно (DB-пароль, API-ключ).

## 3. Перевір перед відправкою

- [x] Чи можна реідентифікувати людину з решти полів? (ім'я+ДН+місто+посада) —
      перевірено: ПІБ, email, телефон, ДН, паспорт, ІПН видалені разом, а не
      частково (комбінація решти полів клієнта не деанонімізує).
- [x] Чи не несе чутливе вставлений URL / скріншот / лог? — так, лог містив
      connection string і API key — обидва замінені на out-of-band плейсхолдер.
- [x] Чи збережена **задача** після санітизації? — так: подвійне нарахування
      комісії, компоненти `preAuthorize()`/`settle()`, acceptance criteria —
      усе лишилось, деталі клієнта/секрети — ні.
- [x] Чи відповідає інструмент/tier категорії даних? (no-train для 🟡) — так,
      див. таблицю нижче.

## 4. Інструмент під категорію (заповни під команду)

| Категорія | Дозволений інструмент / tier | Нотатки |
|---|---|---|
| 🟢 | будь-який публічний асистент (ChatGPT free, публічний Claude.ai) | Загальні описи задач, acceptance criteria без даних — ризик мінімальний. |
| 🟡 | Claude for Work / Copilot Business — **enterprise no-train tier** | Внутрішня логіка (`FeeCalculator`, назва гілки) під NDA: обираємо no-train tier, бо дані компанії (навіть без PII) не мають потрапляти в тренувальні датасети постачальника; enterprise-контракт зазвичай додає DPA і data residency гарантії, яких немає у free tier. |
| 🔴 | **не давати моделям взагалі** — тільки локально / вручну маскувати перед вставкою | Секрети — out-of-band (secret manager), не в промпт і не в документ; PII/банківські дані — тільки masked/synthetic форма йде в будь-який інструмент. |

## 5. Якщо стався витік

- [x] Ротувати скомпрометовані секрети негайно. — приклад: якщо `X-API-Key`
      або DB-пароль з логу реально потрапили в чат з AI — ротувати ключ і
      пароль в PostgreSQL негайно, незалежно від того, публічний інструмент
      чи enterprise.
- [x] Нотифікувати відповідального (security/lead).
- [x] Зафіксувати інцидент і оновити цей чек-ліст (додати кейс у розділ 1/2,
      якщо виявлено нову категорію чутливих даних).
