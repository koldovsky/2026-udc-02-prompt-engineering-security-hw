# Чек-ліст санітизації даних для AI

> Скопіюйте цей файл у `docs/sanitization-checklist.md` і доповніть під свою
> команду. Мета — багаторазовий документ, який можна принести колегам.

## 1. Класифікуй (світлофор)

- [ ] **🔴 Ніколи публічним:** секрети (ключі, токени, паролі, connection strings),
      PII (ім'я, email, телефон, ДН, паспорт, ІПН), банківська таємниця
      (картка, CVV, IBAN, рахунок, баланс), production-дані/дампи,
      медичні/держ./регульовані дані.
- [ ] **🟡 Лише enterprise/no-train:** внутрішній код під NDA, бізнес-логіка,
      схеми БД, архітектура, тікети з контекстом, анонімізовані логи.
- [ ] **🟢 Можна публічним:** публічний/OSS-код, синтетика, загальні питання,
      документація без даних, стек-трейс без значень.
- [ ] **Регіональні вимоги:** GDPR (EU), PII-закон (УКР), PCI DSS (платежи) —
      знай, які закони покривають твої дані перед санітизацією.
- [ ] **Сумнів → 🔴:** якщо невпевнений у категорії — вважай найбезпечнішою,
      не публіковуй без ревью.

## 2. Очисти (техніка під категорію)

- [ ] **Redaction** — прибрати повністю (`[REDACTED]`): те, що не потрібне задачі.
- [ ] **Masking** — зберегти формат, прибрати значення (`****-1234`, `<IBAN>`):
      коли моделі потрібна структура.
- [ ] **Synthetic** — підмінити реалістичним вигаданим: коли потрібні «справжні
      на вигляд» дані для відтворення.
- [ ] **Секрети — out-of-band:** не маскувати, а **не давати взагалі**
      (env / secret store); якщо «світилися» — ротувати.
- [ ] **За форматом даних:** JSON/CSV → прибрати поля; скріншоти → замаскувати
      чутливі зони; логи → маскувати `[PHONE]`, `[IP]`.
- [ ] **Перевір реідентифікацію:** ім'я+ДН+місто+посада = можна знайти людину?
      Якщо так → ще більше маскувати.

## 3. Перевір перед відправкою

- [ ] Чи можна реідентифікувати людину з решти полів? (ім'я+ДН+місто+посада)
- [ ] Чи не містить чутливе вставлений URL / скріншот / лог?
- [ ] Чи збережена **задача** після санітизації?
- [ ] Чи відповідає інструмент/tier категорії даних? (no-train для 🟡)
- [ ] **Peer-review санітизації:** попросити колегу перевірити перед тим,
      як давати моделі.
- [ ] **Лист аудиту:** запишіть хто, кому, коли передав і що (для
      post-mortem якщо щось потрапить не туди).

## 4. Інструмент під категорію (заповни під команду)

| Категорія | Дозволений інструмент / tier | Нотатки |
|---|---|---|
| 🟢 | <напр. будь-який> | |
| 🟡 | <напр. Copilot Business / Claude for Work — no-train> | |
| 🔴 | <не давати моделям; лише локально/маскувати> | |

- [ ] **Автоматична перевірка:** `git secrets --scan` перед push,
      `repomix --ignore .env` при генерації контексту.
- [ ] **Транспорт:** не просто виберіть інструмент, а визначте
      "як передавати" (приватний чат, locked Doc, no-train tier).

## 5. Якщо стався витік

- [ ] Ротувати скомпрометовані секрети негайно.
- [ ] Нотифікувати відповідального (security/lead).
- [ ] Зафіксувати інцидент і оновити цей чек-ліст.
- [ ] **Якщо коллега помилився:** не ігнорувати, приватно нотифікувати,
      якщо вже in-transit — створити issue для видалення з історії.
- [ ] **Post-mortem:** не просто ротувати ключ, але оновити чек-ліст
      і навчити, як помилка могла статись.

## 6. Обґрунтування вибору інструмента для 🟡-даних

### Які 🟡-дані у вас
- [ ] Архітектура системи, схеми БД
- [ ] Назви компонентів, гілок, внутрішні API
- [ ] Бізнес-логіка, тікети з контекстом

### Обраний інструмент/tier
**Claude no-train** (або Copilot Business, або Enterprise)

### Чому саме цей
- [ ] **Безпека:** модель не тренується на наших даних
- [ ] **Compliance:** відповідає NDA/регулюванням
- [ ] **Стійкість / Ціна:** дані залишаються локально / в EU (якщо потрібна GDPR)
- [ ] **Ціна/якість:** баланс між вартістю та функціоналом для внутрішнього використання
