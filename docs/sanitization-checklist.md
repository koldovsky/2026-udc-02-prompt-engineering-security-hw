# Чек-ліст санітизації даних для AI

> Багаторазовий чек-ліст: проходьте його перед тим, як дати будь-який реальний
> документ (тікет, лог, дамп, скрін) AI-інструменту. Для повторюваних форматів
> автоматизуйте кроки 1–2 скриптом — у цьому репо це `scripts/sanitize.mjs`
> (`node scripts/sanitize.mjs <in> <out>`), який працює **локально** й ніколи не
> відправляє оригінал у модель.

## 0. Золоте правило

- [ ] Оригінал із 🔴-даними **ніколи** не потрапляє в публічну модель — ні в
      промпт, ні у вкладення. Санітизація відбувається **локально** (вручну або
      скриптом), і лише результат можна ділити.

## 1. Класифікуй (світлофор)

- [ ] **🔴 Ніколи публічним:** секрети (ключі, токени, паролі, connection
      strings), PII (ім'я, email, телефон, ДН, паспорт, ІПН/РНОКПП), банківська
      таємниця (картка, CVV, IBAN, рахунок, баланс), production-дані/дампи,
      медичні/держ./регульовані дані.
- [ ] **🟡 Лише enterprise/no-train:** внутрішній код під NDA, бізнес-логіка,
      назви компонентів/класів/методів, гілки, схеми БД, тікети з контекстом,
      анонімізовані логи.
- [ ] **🟢 Можна публічним:** публічний/OSS-код, синтетика, загальні питання,
      документація без даних, стек-трейс без значень, acceptance criteria.
- [ ] Сумнів → вважати 🔴.

## 2. Очисти (техніка під категорію)

- [ ] **Redaction** — прибрати повністю (`[…_REDACTED]`): те, що не потрібне
      задачі (email, телефон, ДН, паспорт, ІПН, баланс).
- [ ] **Masking** — зберегти формат, прибрати значення (`XXXX-XXXX-XXXX-1234`,
      `<IBAN>`): коли моделі потрібна структура, а не вміст.
- [ ] **Synthetic** — підмінити реалістичним вигаданим (`[CUSTOMER_1]`,
      `TX-0001`): коли потрібні «справжні на вигляд» дані для відтворення/кореляції.
- [ ] **Секрети — out-of-band:** не маскувати, а **видаляти** (`<SECRET_OUT_OF_BAND>`);
      реальне значення живе в env / secret store. Якщо «світилося» — **ротувати**.

## 3. Перевір перед відправкою

- [ ] Прогнати **leak-check** (наш скрипт робить це автоматично й падає з
      кодом 2, якщо вцілів секрет/PII-патерн).
- [ ] Чи можна реідентифікувати людину з решти полів? (ім'я+ДН+місто+посада)
- [ ] Чи не несе чутливе вставлений URL / скріншот / лог-рядок?
- [ ] Чи збережена **задача** після санітизації? (баг усе ще відтворюваний)
- [ ] Чи відповідає інструмент/tier категорії даних?

## 4. Інструмент під категорію

| Категорія | Дозволений інструмент / tier | Чому |
|---|---|---|
| 🟢 | будь-який (ChatGPT, Claude.ai, Copilot Individual) | немає чутливого — публічний tier ок |
| 🟡 | **no-train enterprise:** Claude for Work / Team, ChatGPT Enterprise/Team, Copilot Business — з вимкненим навчанням на даних і, де можливо, data residency в ЄС | внутрішня логіка/код під NDA: не можна дозволяти потрапити у тренувальні дані постачальника |
| 🔴 | моделям **не давати взагалі**; лише локально / після маскування → результат піднімається максимум до 🟡-tier | секрети/PII/банківська таємниця — регуляторний і репутаційний ризик |

**Вибір для 🟡 у цьому кейсі (JIRA-4821):** назви `payments-core` /
`FeeCalculator.applyTransferFee` потрібні, щоб модель зрозуміла баг, але це
внутрішня логіка. Тому — **enterprise no-train tier** (напр. Claude for Work із
вимкненим навчанням), де дані не йдуть у тренування й, бажано, зберігаються в ЄС
(data residency). Гілку `feat/PSD2-fee-refactor` додатково маскуємо
(`<internal-branch>`), бо вона не потрібна для розуміння бага.

## 5. Якщо стався витік

- [ ] **Ротувати** скомпрометовані секрети негайно (ключі, паролі, DSN).
- [ ] Нотифікувати відповідального (security / team lead).
- [ ] Зафіксувати інцидент і оновити цей чек-ліст / правила скрипта.
